# Theming

Four independent axes, all attributes on the root element. They compose;
none of them is a separate build.

| Axis      | Attribute      | Values                                  |
| --------- | -------------- | --------------------------------------- |
| Brand     | `data-brand`   | absent (consulting), `coaching`         |
| Theme     | `data-theme`   | absent (light), `light`, `dark`, `auto` |
| Density   | `data-density` | absent (cozy), `compact`, `comfortable` |
| Direction | `dir`          | `ltr`, `rtl`                            |

Flip all four from the toolbar above. Nothing here is a preview trick:
the toolbar sets the same attributes a product sets.

A fifth axis has no attribute, because it is not ours to set: the
reader's own text size. Every length in the library is a rem, and
`font-size` is set on `body` and never on `html`, so a browser text
preference scales the whole system. Control heights are measured at two
root font sizes in CI for exactly that reason.

Brand and density are the two that also work on a **subtree** — a
compact toolbar in a cozy page, or one product area under a different
brand. Theme is root-only in practice, because a page with two colour
schemes has bigger problems than tokens.

## Adding a brand

One file, and no core file changes. That last part is the property that
makes multi-brand scale — brands cannot collide in a shared file, so two
teams adding two brands never touch the same line.

```css
/* src/styles/brands/harbour.css — the shape a brand takes */
@layer tokens {
  [data-brand="harbour"] {
    /* colour */
    --uix-accent: var(--uix-teal-600);
    /* shape */
    --uix-radius-control: 0.25rem;
    --uix-radius-container: 0.375rem;
    /* type */
    --uix-font-display: "Söhne Breit", var(--uix-font-sans);
    /* elevation */
    --uix-elevation-raised: none;
  }

  /* Both spellings. A brand is often scoped to a subtree while the theme
     sits on the root, so the compound selector alone never matches: it
     demands both attributes on one element. A brand nested under a dark
     root kept its light accent that way, measured at 2:1. */
  [data-brand="harbour"][data-theme="dark"],
  [data-theme="dark"] [data-brand="harbour"] {
    --uix-accent: var(--uix-teal-400);
  }
}
```

Import it from `styles.css` and you are done. Two gates then apply:

- **A brand may only re-point semantic tokens.** A test reads the brand
  file and fails on anything else. Reaching into a primitive would change
  every brand; reaching into a component token would fix one component
  and leave its siblings behind.

  The other half of that rule is what makes it usable: whatever a brand
  must be able to change has to _have_ a semantic role. For a long time
  radius, typeface and shadow were primitives and components named them
  directly, so the brand axis was colour-only — and a brand re-pointing
  one token was the ceiling rather than a demonstration. There are now
  shape, type and elevation roles, and a test forbids a component from
  naming any of the four primitive families.

  `coaching` is the reason that mattered. A leadership-coaching practice
  and a consulting practice do not differ by hue; they differ by how much
  room the page takes and how hard its corners are. That is only sayable
  if radius, type, elevation and density are all semantic.

- **Contrast is measured for the new brand automatically.** The check
  walks every declared pairing in every theme for every brand it finds on
  disk. A brand that cannot clear WCAG AA fails the build rather than
  shipping.

## What follows the accent on its own

`coaching` never mentions a hover colour, a focus ring or a wash.
Everything derived from the accent moves with it:

- `--uix-accent-soft` is a `color-mix` of the accent, not a second hex
  value someone has to remember to update.
- `--uix-focus-ring` aliases the accent.
- Hover and active states mix the fill toward `--uix-ink` or
  `--uix-paper`, which flip per theme, so a hover deepens on light and
  brightens on dark without either being written down twice.

That is the test of a semantic layer: how few values a brand has to
supply before the rest is implied. `coaching` supplies nine — one colour,
four shapes, a typeface, three elevations — plus the density multiplier,
and gets a consistent identity across thirty-four components from it.

## Theming one component without touching another

Component tokens are override slots. They are not declared anywhere; each
is referenced with its semantic default inline:

```css
.uix-button[data-tone="accent"] {
  background: var(--uix-button-accent-bg, var(--uix-accent));
}
```

So a product that needs a different button fill sets one custom property
and inherits everything else. The slot costs nothing until it is used,
which is why the tier can cover every component without the stylesheet
growing.

```css
/* a product, not the design system */
@layer overrides {
  .checkout {
    --uix-button-accent-bg: var(--uix-status-ok);
  }
}
```

Use the `overrides` layer for this. Unlayered CSS outranks every layer,
so styling from outside the layers silently beats the whole system.

## Density

`data-density="compact"` sets one multiplier, and the semantic
`--uix-gap-*` and `--uix-control-*` roles carry it into padding, gaps,
margins and control heights alike. At the default density they resolve to
the raw scale exactly, so cozy rendering is byte-identical to no density
at all.

Two things about it are easy to get wrong, and both are held down by
tests rather than by this page.

**It works on a subtree, and that took a fix.** A custom property has its
`var()` substituted on the element where it is _declared_. Declared only
on `:root`, `--uix-control-md` resolved the density at the root and every
descendant inherited the finished value, so a `data-density="compact"`
subtree inherited the page's heights and changed nothing — while this
guide said it would. The density roles are now declared on
`:root, [data-density]`, so any element carrying the attribute
re-resolves them against its own multiplier.

**A density cannot make a control illegal.** The heights are
`max(24px, calc(<rem> * var(--uix-density)))`. At the compact multiplier
of 0.72 the small height resolved to 23.04px, under the WCAG 2.2 target
size minimum. The clamp lives in the token rather than in a larger
multiplier, so a product that supplies its own density cannot
reintroduce the violation.

`--uix-density` is registered with `@property` as a `<number>`. An
unregistered property accepts anything, and one typo — `medium` — would
make every `calc()` in the page invalid at computed-value time. The
derived roles stay unregistered on purpose: they are computed from an
already-validated input, so there is nothing left to check.
