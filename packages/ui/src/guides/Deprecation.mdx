# Deprecating a token

Deprecate a token when consumers should move to another name or design role.
Provide the replacement and migration window before removing it. A token with
no uses in this repository may still be used by a consuming application.

## Inspect its uses

```sh
pnpm nx run ui:tokens-report
```

The report follows aliases as well as direct uses. A primitive remains in use
when a semantic role references it, even if no component names the primitive.
Review the call sites and the role the token serves before choosing a replacement.
The report also identifies references to undeclared tokens.

## Record the migration

In `tokens.registry.ts`, give the token a reason, replacement, deprecation date
and earliest removal date. For example, a hypothetical rename could use:

```ts
t(
  "--uix-example-old-fill",
  "var(--uix-bg-surface)",
  "component",
  "color",
  "Example fill",
  "Use --uix-example-bg to match the component's other slots.",
  "--uix-example-bg",
  { deprecatedOn: "2026-09-26", removeAfter: "2027-03-26" },
),
```

Choose dates for the actual migration rather than copying this example's dates.
If a name changes but its meaning does not, add the new name and keep the old
one as an alias during the window. Describe the compatibility impact and
migration in the changelog. Component slots also need their consumers and
inline fallbacks reviewed.

The DTCG export carries the deprecation reason and the migration metadata, so
consuming tools can read it without parsing a prose explanation.

## Migrate call sites

Use `pnpm nx run ui:tokens-codemod` to inspect supported replacements before
applying changes. Review each affected component and its states. A name change
can be mechanical; a change in meaning may need a different design choice.

The usage baseline records the tolerated count of each deprecated token. New
uses fail the check. After reducing uses, update the baseline so the old count
cannot silently return:

```sh
pnpm nx run ui:tokens-baseline
pnpm nx run ui:tokens-check
```

Review the baseline diff. Updating it is not a reason to accept new deprecated
uses. Existing uses remain subject to the recorded migration deadline.

## Complete the removal

The check fails when a deprecated token has no window or its removal date has
passed. If no uses remain, remove the token and registry entry along with the
obsolete compatibility code. If uses remain, finish the migration or deliberately
revise the date with a reason.

A zero count establishes repository usage only. Confirm the migration with
consumers before removing a public token, then run `pnpm gates` and inspect the
affected examples in both themes.
