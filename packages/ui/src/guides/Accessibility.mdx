# Accessibility

Start with the complete task: how someone finds the controls, understands the
instructions, corrects a mistake and knows the action has finished. The shared
components provide much of the wiring. The application supplies meaningful
content and an interaction that can be completed.

## Label the control and explain the error

Use TextField when you need a labelled text input. Give the label a stable name,
put supporting instructions in `hint`, and explain a failed requirement through
`error`. Set `required` on the control instead of adding that word or an asterisk
to the label yourself.

The feature validates the value. Form supplies the summary, and TextField uses

this example present its own messages instead of a native validation popup;
the required state still belongs on the input.

For a custom control, spread Field's returned `control` object onto the actual
control. Checkbox, Switch and other choice controls already provide their own
label layout and field-message wiring.

## Make changes understandable

State what happened and what the reader can do next. Keep the status message
close to the action and use a live region when a change needs announcing without
moving focus. Avoid announcing the same message in several places.

Keep status meaning in text. Colour and icons can reinforce an error or a
success, but someone must be able to understand it without distinguishing the
colours. Preserve a visible label; placeholder text disappears during entry.

A loading Button retains focus with `aria-disabled` and blocks activation.
A native disabled Button is unavailable and may leave the tab order. Use the
state that matches the operation, and make the operation's result clear.

## Follow the task with a keyboard

Start before the first control and use Tab, Shift+Tab, Enter, Space and the
component's documented keys. Check where focus moves after opening a dialog,
closing it, reporting an error and returning to the page. The Keyboard guide
lists the supported component behavior.

Repeat at a narrow width and with larger text. Controls must remain visible and
reachable; reading order and focus order should still make sense when columns
stack. Inspect the focus indicator against the actual backgrounds it crosses.

## Check the accessible information

Use accessible-name and description assertions to check the label and supporting
text. Inspect roles, states and the accessibility tree to understand the order
of information. Those checks cannot establish what a particular screen reader
speaks or when it speaks it, so complete the task with the intended reader and
browser as well.

Record the component or page, versions, date, steps, observed speech and any
problems. No completed manual screen-reader passes are currently recorded.

## What we test and known limitations

Story tests run axe in light and dark themes. Browser tests cover selected
keyboard interactions, names, descriptions, accessibility trees and assembled
page layouts. Contrast checks measure the registered token pairings.

Run `pnpm gates` after a change and inspect the relevant examples. These checks
establish their assertions for the tested fixtures. They do not establish
accessibility for every composition, override or assistive-technology setup.

The application supplies content, navigation and integrations. Check the complete
task with those in place; component checks do not establish application-wide
conformance. Automated accessibility-tree checks also cannot establish spoken
phrasing, timing or usability with a particular screen reader.
